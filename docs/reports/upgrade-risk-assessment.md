## 三、升级风险矩阵

### 风险类别

| 风险等级 | 影响范围 | 风险描述 |
|---------|---------|---------|
| 🔴 **极高** | 后端核心 | 计费系统（分层定价、组切换、配额预消耗）完全重构 |
| 🔴 **极高** | 后端核心 | 渠道和路由逻辑重构（auto-group、模型发现、responses API） |
| 🔴 **高** | 后端安全 | 认证系统从 session-based → stateless token |
| 🟠 **高** | 后端功能 | OpenAI Responses API 路由和计费变更 |
| 🟠 **高** | 前端 | Default 主题 UI 变更（渠道表、Playground、JSON 编辑） |
| 🟡 **中** | 后端性能 | Zstd 压缩、HTTP 传输控制 |
| 🟡 **中** | 运维 | 日志格式变更、流指标新增 |
| 🟢 **低** | 前端 | 浏览器翻译防护、渠道表列宽调整 |

### 具体风险项

#### 🔴 极高风险

1. **计费回归**
   - v1.0.0-rc.20~23 有 4 次重大计费修复
   - 分层定价（tiered pricing）+ 组切换计费是新逻辑
   - **风险**: 计费错误会导致财务损失
   - **缓解**: 建立计费测试套件，模拟所有计费场景

2. **渠道路由重构**
   - 新增 auto-group 路由、模型发现、responses API 路由
   - **风险**: 请求路由错误导致服务中断
   - **缓解**: 逐渠道测试，生产灰度发布

3. **认证系统变更**
   - Session-based → stateless tokens 是根本性变更
   - **风险**: 用户登录失败、权限绕过
   - **缓解**: 全面回归测试认证流程

#### 🔴 高风险

4. **Vancine 特色功能丢失**
   - Google OAuth、Turnstile、i18n 懒加载、暗色主题优化
   - **风险**: 升级覆盖自定义代码
   - **缓解**: 维护清晰的 patch 分支，手工合并

5. **数据库 schema 变更**
   - 13 个版本累积可能有 migrations
   - **风险**: 升级导致数据库结构不一致
   - **缓解**: 逐版本检查 migration，先在 staging 测试

#### 🟠 高风险

6. **前端组件不兼容**
   - Default 主题基于 React 19 + TanStack，上游可能有依赖更新
   - **风险**: 组件 API 变更导致构建失败
   - **缓解**: 检查 package.json diff，逐个升级依赖

7. **配置选项变更**
   - 新功能可能引入新的配置项（HTTP transport、auto-group 等）
   - **风险**: 缺少配置导致功能异常
   - **缓解**: 研读 release notes，补全缺失配置

#### 🟡 中风险

8. **性能回退**
   - Zstd 压缩、HTTP 传输控制可能影响连接性能
   - **风险**: 延迟增加、吞吐下降
   - **缓解**: 性能基准测试，逐项验证

9. **日志和监控**
   - 日志格式变更可能影响现有的监控系统
   - **风险**: 监控告警失效、数据丢失
   - **缓解**: 更新日志解析规则

## 四、升级策略建议

### 方案 A：渐进式合并（推荐）✅

**适用场景**: 风险容忍度低、业务稳定期

**步骤**:
1. **v1.0.27**: 同步 v1.0.0-rc.10→rc.15 的基础变更（2-3 周）
   - 合并 bug 修复、i18n、渠道管理
   - 避开计费、认证等核心变更

2. **v1.0.28**: 同步 v1.0.0-rc.16→rc.20 的计费框架（3-4 周）
   - 建立计费测试套件
   - 逐功能合并和验证

3. **v1.0.29**: 同步 v1.0.0-rc.21→rc.23 的新特性（2-3 周）
   - responses API、auto-group、New API 渠道
   - 全面回归测试

**优点**: 降低风险、易于调试、可回滚
**缺点**: 周期长（7-10 周）、需持续投入

### 方案 B：全量升级

**适用场景**: 急需新功能、有足够的测试覆盖

**步骤**:
1. 创建升级分支（`upgrade/v1.0.0-rc.23`）
2. 对比上游 diff（3000+ commits）
3. 手动合并 Vancine 特色代码
4. 全面测试（2-3 周）
5. 灰度发布

**优点**: 一次到位、新功能立即可用
**缺点**: 风险高、调试困难、可能遗漏 Vancine 自定义代码

### 方案 C：延迟合并

**适用场景**: 等待上游稳定

**策略**:
- 维持现有版本（v1.0.26），不升级
- 仅合并安全修复（如需要）
- 等到 v1.0.0 稳定版或 v1.1.0

**优点**: 最小风险、维护成本低
**缺点**: 缺少新功能、技术债务累积

## 七、回滚策略

### 回滚条件

以下情况必须回滚：
1. 计费错误率 > 0.1%
2. 服务不可用时间 > 5 分钟
3. 用户投诉率上升 > 10%
4. 安全漏洞（认证绕过）

### 回滚步骤

1. **停止新版本**: `docker compose down`
2. **恢复旧版本**: `git checkout v1.0.26 && docker compose up -d`
3. **数据库恢复**: 如有 migration，运行回滚脚本
4. **通知用户**: 系统维护通知
5. **调查根因**: 分析回滚原因，修复后重新发布

### 回滚影响

- **数据**: 如有新表/字段，回滚后这些数据会丢失
- **用户会话**: 需要用户重新登录
- **配置**: 新配置项会被忽略（不影响旧功能）
